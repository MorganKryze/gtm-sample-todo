## Review focus
1. Date validation in `parseDue` (Task 1, test `parseDue refuses a date that is not a real
   YYYY-MM-DD day`): no rollover (`2026-02-30`), no loose forms (`2026-2-3`, ISO with a time),
   a real leap day (`2028-02-29`) accepted (lens: Inversion Analysis).
2. A refused date leaves the file byte for byte unchanged (Task 1, test `cli add refuses a bad or
   missing due date and leaves the file unchanged`): the throw happens before `save`.
3. Old files (Task 1, test `cli keeps an old file without due unchanged`): no `due` key added to
   existing or undated todos, ids untouched.
4. Time zones (Task 2, test `localDate reads the local calendar day at any hour`, plus the two
   `TZ=` runs): no `Date` built from the stored string anywhere in `format` (lens: Pre-mortem Analysis).
5. Overdue boundary (Task 2, test `format marks an open todo overdue only before today`): due
   today is not overdue, done is never overdue; plain string comparison of two `YYYY-MM-DD` values.

## Decisions made where the spec is silent
1. `--due` may stand anywhere after `add`; the first `--due` and the word after it are the option,
   the rest is the text (`todo add --due 2026-11-02 buy milk` works). A second `--due` stays in
   the text. (cost if wrong: a todo text holding a stray `--due`; the person re-adds it.)
2. Messages: missing date `--due needs a date YYYY-MM-DD`; bad date `bad due date <text>, use
   YYYY-MM-DD`. (cost if wrong: one string to reword, its test with it.)
3. Line form: `[ ] #1 buy milk (due 2026-11-02)`, overdue `[ ] #2 call bob (due 2026-10-01,
   overdue)`. (cost if wrong: a format tweak in one function and two tests.)
4. `format(items, today = localDate())`: today is a parameter so the logic stays pure and the
   tests pin the date; the existing `format([])` test keeps working unchanged. (cost if wrong:
   none for users; one call site.)
5. `add` checks the text before the date, so an empty text with a bad date reports the text.
   (cost if wrong: the person fixes two mistakes one at a time.)
6. Years are four digits, any value (`0001` to `9999`), no range check beyond a real day.
   (cost if wrong: a far-off typo like `2062` is accepted; it shows on `list`.)
